# React 코드 품질 가드

사용자에게 보이는 동작과 계약을 지키면서 React 코드의 오류 가능성, 변경 비용, 불필요한 작업을 줄인다. Vercel React Best Practices의 성능 관점을 활용하되 규칙 개수·폴더 모양·메모이제이션 개수를 품질로 취급하지 않는다.

## 작업과 환경부터 맞추기

요청이 구현·개선인지, 계획·리뷰만인지 구분한다. 리뷰·계획 요청에서는 소스·설정·문서를 수정하지 않는다. 개선까지 요청받으면 필요한 변경과 검증까지 진행한다.

관련 package.json·잠금 파일·빌드 설정에서 React 버전, JS/TS, SPA/SSR/RSC, 라우터·데이터 라이브러리, React Compiler 활성화 여부를 확인한다. React 프로젝트라는 이유로 Next.js나 최신 API를 전제하지 않는다. 버전별 API가 필요하면 설치된 버전의 타입·코드와 공식 문서를 대조한다. 패키지나 빌드 도구 교체는 별도 목적이 있을 때만 다룬다.

사용자가 지정한 파일·기능·diff에서 시작해 직접 소비자와 상태·요청 경로를 확인한다. 로컬 변경은 staged·unstaged·새 파일을 포함하고 기존 사용자 변경과 구분한다. 전체 감사는 요청받았거나 국소 조사로 원인을 판단할 수 없을 때만 넓힌다.

## 판단과 개입

정확성·데이터 격리·호환성 문제를 먼저 해결한다. 성능은 실제 사용자 경로의 요청 직렬화, 초기 전송량, 비싼 렌더·구독부터 조사하고 미세 최적화는 비용이 확인된 경로에 한정한다. 원문의 우선순위나 개선 수치를 현재 프로젝트의 측정 결과로 옮기지 않는다.

관찰한 코드 → 발생 조건 → 동작 또는 비용에 미치는 영향 → 가장 작은 조치 → 확인 방법을 연결한다. 렌더 횟수 증가만으로 체감 성능 저하를 확정하지 않고, 측정이 없으면 성능 효과를 가설로 표시한다. 명백한 상태 오류나 중복 Effect 제거에 불필요한 벤치마크를 선행 조건으로 걸지 않는다.

컴포넌트·훅 분리는 상태 생명주기, 비싼 작업, 재사용되는 동작을 실제로 분리할 때 선택한다. 파일 길이만으로 분할하거나 새 서비스·상태관리 계층을 추가하지 않는다. 프로젝트 경계까지 바뀌면 기존 설계 지침과 대조한다. `architecture-guard`가 함께 요청된 경우 경계 검토 결과를 재사용하고 같은 문제를 중복 보고하지 않는다. 이 스킬이 다른 스킬을 자동으로 요구하지는 않는다.

## 검증과 완료

바꾼 동작에 맞는 기존 lint·타입 검사·테스트를 사용한다. Hooks 규칙이나 타입 검사를 약화시켜 통과시키지 않는다. 상태·비동기 수정은 재현 조건에 맞는 상호작용이나 회귀 테스트로 확인하고, 성능 수정은 가능하면 같은 빌드·입력·기기 조건의 프로파일·네트워크·번들 결과를 비교한다. 이미 충분히 검증된 저위험 변경에 검사를 계속 늘리지 않는다.

최종 보고는 작업 규모에 맞게 짧게 한다. 근거 있는 문제를 중요도순으로 제시하고 파일·심볼, 영향, 수정 또는 제안을 연결한다. 실행한 검사와 미실행 항목, 측정한 효과와 예상 효과를 구분한다. 심각한 미해결 문제가 있으면 명시하고, 발견한 문제가 없으면 검토 범위 안에서 없다고 말한다. 점수·지적 개수를 채우기 위한 리팩토링은 하지 않는다.
