# 아키텍처 유지보수 가드

변경이 누적되어도 책임과 의존성이 명확하고, 다음 변경을 국소적으로 이해·수정·검증할 수 있는 설계를 유지한다. 폴더 모양이나 패턴 준수보다 실제 변경 비용과 실패 위험을 판단한다.

## 작업에 맞게 적용

- 착수 전 점검·설계·계획: [preflight.md](references/preflight.md)를 읽는다.
- 구현 후 검토·PR 리뷰·아키텍처 진단: [review.md](references/review.md)를 읽는다.
- 구현·수정까지 요청받은 경우: 필요한 사전 점검 → 요청된 구현 → 최종 변경 검토를 수행한다. 계획에서 불필요하게 멈추지 않는다.

현재 단계에 필요한 문서만 읽는다. 상위 지시와 사용자의 작업 범위·출력 형식을 따른다. 스킬 호출 자체는 코드 수정 권한이 아니다. 계획·리뷰만 요청받았다면 소스·설정·문서를 수정하지 않는다. 기존 검증 도구의 임시 산출물은 별개로 취급한다.

## 판단의 근거와 범위

적용되는 저장소 지침, 관련 설계 결정과 경계 규칙, 실제 코드·호출부·검증 설정을 확인한다. 이미 제공된 정보는 재사용하고 작업에 필요한 부분만 읽는다. 명시된 규칙과 코드에서 추론한 관행을 구분하고, 둘이 충돌하면 차이를 밝힌다. 기존 관행이라는 이유만으로 결함을 정당화하지 않는다.

변경 파일에서 시작해 영향을 받는 호출자·피호출자·공개 계약·상태 소유자를 따라간다. 여러 경계에 영향이 확인되면 필요한 만큼 확장하되, 전역 감사는 요청되었거나 국소 조사로 위험을 판단할 수 없을 때만 수행한다. 코드를 볼 수 없다면 가정 기반 조언과 실제 검토를 명확히 구분한다.

아키텍처 영향이 없는 문구·서식 변경은 경량 확인으로 종료한다. 명시적 전체 감사가 아니라면 기존 기술부채와 이번 변경에서 새로 생기거나 악화된 문제를 분리한다.

## 유지해야 할 성질

관련 있는 항목만 판단한다. 모든 항목을 채우기 위한 보고서를 만들지 않는다.

- **책임과 응집도:** 같은 이유로 바뀌는 정책이 적절한 소유자에 모여 있는가? UI·전송·저장·업무 정책의 혼합 때문에 무관한 곳까지 수정해야 하는가?
- **경계와 의존성:** 합의된 의존 방향과 공개 진입점을 지키는가? 내부 구현 직접 참조, 순환 의존, 상위 기능을 아는 공용 코드가 생기는가? import뿐 아니라 이벤트·전역 상태·콜백·네트워크를 통한 결합도 관련 범위에서 본다.
- **상태와 계약:** 데이터·정책의 기준점과 쓰기 책임이 명확한가? 변경된 API·타입·캐시·이벤트·스키마의 소비자가 호환되는가? 권한·테넌트·동시성·트랜잭션 경계를 건드리면 그 불변조건도 확인한다.
- **변경의 국소성과 검증:** 같은 정책 변경을 여러 곳에서 동기화해야 하는가? 핵심 동작을 과도한 환경·전역 상태 없이 검증할 수 있는가?
- **복잡성의 정당성:** 새 계층·공통화·인터페이스·의존성이 현재 확인된 문제를 줄이는가? 호출 경로와 개념만 늘리거나, 서로 다르게 진화해야 할 코드를 묶지는 않는가?

폴더명, 파일 길이, 중복 개수만으로 결함을 확정하지 않는다. DTO 변환, 서비스 계층, 공개 barrel, DDD·FSD·Clean Architecture 등을 일괄 강제하지 않는다. React라면 상태 소유권·effect·서버 캐시와 UI 정책의 결합을 보되 특정 폴더 구조를 전제하지 않는다.

## 개입의 기준

현재 구조 유지, 국소 수정, 경계 조정 중 실제 문제를 해결하는 가장 작은 대안을 고른다. 추상화는 없애는 결합과 새로 만드는 비용을 함께 설명할 수 있을 때 도입한다. 반복되는 문제는 공통 원인을 확인한 뒤 소유 경계에서 해결하고, 단발 문제는 전체 재설계로 확대하지 않는다.

수정이 허용된 경우 요청된 동작과 호환성을 보존한다. 의도된 계약 변경은 영향과 전환 방법을 검증한다. 무관한 리팩토링, 사용자 변경 덮어쓰기, 검사를 통과시키기 위한 규칙 완화는 하지 않는다. 범위를 벗어나는 계약 변경이나 위험한 마이그레이션은 제안으로 분리한다.

기존 lint·타입 검사·의존성 규칙·테스트를 우선 활용한다. 반복 가능한 중요한 경계 규칙은 구현 범위에 맞는 작은 자동 검사로 남길 수 있다. 범용 검증 프레임워크나 새 패키지를 기본으로 추가하지 않는다. 설계 결정이 실제로 바뀌었다면 해당 문서만 갱신하며, 지침 파일을 매번 증식시키지 않는다.

## 완료와 전달

관찰된 코드 → 위반한 경계 또는 정책 → 구체적인 유지보수·동작 영향 → 최소 조치 → 확인 방법을 연결한다. 근거 없는 가능성은 확정 결함 대신 확인 필요 항목으로 둔다. 취향 차이를 차단 사유로 삼지 않는다.

보고는 중요도순으로 간결하게 한다. 지적에는 파일·행 또는 심볼과 실제 의존·호출 경로를 붙인다. 실행한 검증, 결과, 실행하지 못한 검증을 구분한다. 테스트 통과만으로 아키텍처 전체를 보증하지 않는다. 문제가 없으면 조사 범위 안에서 없다고 말한다. 점수나 지적 개수를 채우려고 문제를 만들지 않는다.

새로 생기거나 악화된 중대한 문제가 해결되었거나 명시적으로 미해결로 보고되고, 관련 검증의 상태와 한계가 드러나면 종료한다. 중대한 문제가 남거나 중요한 근거가 부족하면 승인된 것처럼 표현하지 않는다. 선택적 개선을 없애기 위한 무한 리팩토링은 하지 않는다.
