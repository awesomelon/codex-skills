# 작업 후 아키텍처 리뷰

목표는 최종 변경이 유지보수성과 경계를 보존하는지 확인하는 것이다. 변경 없는 현재 구조 진단과 diff 리뷰를 혼동하지 않는다.

## 비교 기준

사용자가 지정한 PR·커밋 범위·기준 브랜치를 우선한다. PR은 확인된 base와 head 및 공통 조상(merge-base)을 기준으로 검토한다. 단순한 원격 추적 브랜치를 PR base라고 가정하지 않는다.

로컬 변경 리뷰는 staged·unstaged·untracked 파일을 함께 확인한다. `git diff` 하나만으로 새 파일이나 staged 변경을 놓치지 않는다. 이번 작업의 완료 검토는 작업 시작 시점의 상태와 최종 상태를 구분하여 사용자 기존 변경까지 자신의 변경으로 간주하지 않는다. 커밋된 작업까지 대상이면 해당 범위를 포함한다.

기준이 불명확하면 저장소 상태와 작업 맥락에서 확인 가능한 범위를 정해 밝힌다. 근거 없이 `main`, `HEAD~1`, 원격 최신 상태를 기준으로 삼지 않는다. 비교 자료가 없으면 현재 상태만 조사한 것으로 보고하고, 회귀가 없다고 단정하지 않는다. 넓은 범위에서 일부만 확인했다면 그 표본과 미검토 경계를 밝힌다.

## 검토 방식

diff뿐 아니라 관련 코드와 호출자를 읽어 실제 동작·의존 경로를 확인한다. 경로 별칭·재수출·타입 전용 의존성·코드 생성·동적 등록 때문에 생긴 오해인지 검증한다. 명시적으로 허용된 예외나 단계적 전환을 위반으로 오인하지 않되, 예외의 적용 범위를 확인한다.

변경 전과 비교해 문제가 새로 생겼는지, 기존 문제가 악화되었는지, 무관한 기존 부채인지 구분한다. 기존 부채라도 이번 변경의 안전성이나 계약 준수를 직접 가로막으면 그 연결을 설명한다.

근본 원인이 같은 지적은 묶는다. 파일 이동만으로 의존 문제가 해결되었다고 보지 않는다. 낮은 확신의 후보를 지적 개수에 넣지 말고 확인 필요로 분리한다.

## 지적의 형식

각 지적을 다음 정도로 구체화한다. 별도 리뷰 시스템이 지정한 출력 형식이 있으면 그 형식을 유지하고 내용을 맞춘다.

**[차단 / 개선 / 기존 부채 / 확인 필요] 문제 제목**
- 근거: 확인한 파일·행 또는 심볼, 관련 소비자나 의존 경로.
- 발생 조건과 영향: 어떤 변경·실행 조건에서 어떤 계약·정합성·유지보수 문제가 생기는지.
- 최소 조치와 검증: 가장 작은 수정 또는 확인 방법.

`차단`은 합의된 필수 경계 위반, 소비자 호환성 파괴, 권한·데이터 정합성 위험 등 이번 작업의 완료를 막는 근거 있는 문제다. 유지보수 문제도 핵심 경계를 심각하게 훼손하면 차단이 될 수 있지만, 단순 취향이나 미래의 가상 확장성은 해당하지 않는다. `개선`은 실제 근거가 있으나 현재 변경을 막지는 않는 항목이다.

## 검증과 판정

확인된 프로젝트 명령과 안전한 환경으로 관련 검사·테스트를 실행한다. 리뷰 전용 작업에서는 자동 수정 옵션과 소스 변경을 피한다. 실행되지 않은 명령은 결과가 아니라 제안으로 표시한다. 이미 실패하던 검사와 변경이 유발한 실패를 확인 가능한 범위에서 구분한다.

수정까지 요청받았으면 이번 범위의 문제를 수정하고 최종 diff와 관련 검증을 다시 확인한다. 기존 검사를 비활성화하거나 기대값을 무작정 완화하여 통과시키지 않는다. 중요한 경계 위반을 재현하는 자동 검사를 추가했다면 가능할 때 수정 전 실패·수정 후 통과도 확인한다.

마지막에 범위와 비교 기준, 중요한 지적, 검증 결과와 한계를 남긴다. 기본 판정은 다음 중 하나다.

- **수정 필요:** 해결되지 않은 근거 있는 차단 문제가 있다.
- **추가 확인 필요:** 차단 문제 여부를 판단할 중요한 근거나 검증이 부족하다.
- **검토 범위 내 중대한 회귀 없음:** 중요한 검토와 관련 검증에 충분한 근거가 있고 차단 문제가 없다. 선택적 개선이나 한계는 별도 표시한다.

비교 기준이 없는 현재 상태 감사에서는 '회귀 없음' 대신 '검토 범위 내 중대한 문제 미발견'이라고 한다. 계획한 검사를 실행하지 못한 사실을 숨기거나, 이 판정을 프로젝트 전체의 품질 보증으로 확대하지 않는다.
