Do not adopt the shared transparent disk cache as proposed. The two needs have different consumers, lifetimes, and access policies, and the latency bottleneck is still unmeasured. A host-local cache cannot deliver a portable artifact to contractors whose filesystem is elsewhere.

| Option | Fit and tradeoff |
| --- | --- |
| Retain current behavior | Avoids additional disk and operational obligations, but leaves both outcomes unresolved. Use as the comparison baseline. |
| Extend the existing session object and explicit export command separately | Best starting direction: session reuse can target measured repeat-query cost; the export command can create a portable artifact with explicit size, contents, and expiry semantics. Each policy has a clear existing entry point. |
| Shared transparent disk cache | Adds 1–8 GB storage pressure, eviction and cleanup obligations, and authorization risks without a demonstrated performance benefit. It still needs a separate delivery mechanism and offline policy. No eviction owner is agreed. |

Keep interactive reuse owned by the session/query path. Recheck permission at the access boundary for every use, including cache hits; revocation during a session must prevent subsequent access even when data is already cached. Define invalidation and cancellation behavior for in-flight results. Scope retained state to the appropriate user and trace revision, and bound its lifetime and capacity. An in-memory session object is an existing place to investigate, not proof that retaining an entire 8 GB trace in memory is feasible.

Keep contractor delivery owned by the explicit export path. The artifact must be self-contained and readable offline, with a documented format, size expectations, expiry semantics, and an owner for reader compatibility. Export creation must enforce current access rights. Once delivered, an offline copy cannot reliably honor immediate server-side revocation. Likewise, an expiry field can document a policy or be enforced by a cooperating reader, but cannot guarantee that recipients delete copied data. Resolve whether the required expiry is a documented retention obligation or a stronger access guarantee before committing to the export contract. If immediate revocation is required, unrestricted offline use is incompatible with that requirement.

Parsing or encoding routines may be shared where their actual semantics match. A single cache abstraction does not establish shared retention, authorization, or eviction policy. Do not introduce a distributed service while ownership is unassigned and local remedies remain untested.

The useful next check is a bounded assessment of one representative ten-minute analyst session and one contractor export. For the analyst session, measure parsing, query execution, transfer, rendering, and peak resource use separately on small and large traces; include repeated queries and a permission revocation between accesses. For the export, test the proposed artifact in a clean offline environment without access to the host filesystem, including the agreed expiry behavior. These are proposed checks, not executed prototypes.

If parsing dominates repeats and bounded session reuse helps without stale access or unacceptable memory use, extend session reuse. If transfer or rendering dominates, reject caching as the latency remedy and address that stage. A cache hit that serves revoked data rejects the design regardless of speed. Offline failure without host state rejects the export boundary. Only revisit persistent caching after evidence of a benefit beyond session reuse, a concrete capacity and eviction policy, and confirmed ownership. The available observations already justify splitting the policies; measurements determine whether caching is useful at all.
