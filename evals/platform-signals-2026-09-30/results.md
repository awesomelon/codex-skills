# Platform discovery signals — 2026-09-30

## Change and basis

Get Set's problem-selection reference now treats user workarounds and unintended uses as evidence of unmet outcomes, while preserving differences in consumer policy. It also distinguishes absence of a workaround from low impact and separates adoption barriers by cause before recommending platform expansion. These are conditional investigation cues, not a required discovery phase or a new skill. Entry points, execution strategy, and Go instructions are unchanged.

The source was the user-supplied sujithjay.com article dated September 22, 2026, about inventing platform work. Its text was read from the supplied attachment; no article permalink was supplied or inferred. The [manifest](manifest.json) records its input hash. The designated [OpenAI authoring article](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra) was fetched and read directly in the preceding review in this conversation on September 30, 2026, Asia/Seoul. The change uses contextual reference guidance instead of adding an eleven-signal checklist or expanding skill descriptions.

The English README catalog and current [scenario catalog](../set-go-2026-09-29/cases.md) reflect the use cases. Plugin version advances from 0.5.1 to 0.5.2; marketplace identity and source path remain consistent without a marketplace change.

## Method

Five fresh subagents received no conversation fork, an explicit skill invocation, temporary copies of both skills, and only their task and raw fixture records. They were not given the review, proposed answer, or parent acceptance criteria. Model settings were inherited without overrides or an independent model measurement. Host details, exact wrapper prompts, input and skill hashes, resource reads reported by workers, post-run inventories, and response hashes are in the manifest.

The first migration assessment selected execution-strategy and review-scope rather than the changed problem-selection reference. A fifth, fresh case therefore explicitly named problem-selection while reusing the migration fixture in a separate directory. That case exercises the changed paragraph, not reference routing. The routine case reuses the [earlier typo fixture](../ambiguity-2026-09-30/fixtures/routine/TASK.md) in a fresh temporary copy and is a new run.

Assessment cases permitted no task-file edits; the routine case permitted its requested typo correction. Response records were written outside the assessed directories. Resource restrictions were instructions, not a separate OS sandbox. The host could still advertise instructions and skills inherited by workers.

## Verification and limits

Both skills passed the repository validator, and Get Set passed Skill Creator's quick validator. The default Python first failed because PyYAML was unavailable; the checks then passed using an existing temporary environment with Python 3.11 and the pinned PyYAML 6.0.3. No user Python, installed skill, or Codex configuration was modified. [Structural checks](structural-checks.json) record the commands and final documentation/package checks.

The installer and validator implementations were unchanged, so their regression suites were not rerun. No Plugin Creator validator was found in the installed Codex skill/plugin directories. No installation, host discovery, marketplace registration, or remote release was performed.

These are unpaired explicit-invocation smoke cases, not evidence of improvement over the previous instructions, reliability, automatic skill selection, or cost/latency savings. Three cases read the changed reference; one of those was explicitly directed to it. The fixtures supply synthetic evidence and do not establish behavior with inaccessible real-world records. Resource reads are worker-reported. File assertions establish final contents and inventory, not every intermediate operation. No production migration, interview, integration replay, or application runtime was exercised.
